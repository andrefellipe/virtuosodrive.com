# API Documentation: Virtuoso Drive

Source: code at commit `533329e`. Line numbers refer to `app/public/js/VirtuosoController.js` unless another file is named. Statements marked **(inference)** were reasoned from the code or from documented platform behaviour and not observed running. Defect ids are defined in `code-quality-assessment.md`.

The application publishes no API of its own. Its contracts are:

1. the data it keeps in Firebase Realtime Database,
2. the objects it keeps in Cloud Storage for Firebase,
3. the security rules on both,
4. the hosting configuration,
5. two routes in an Express scaffold that is not deployed.

## 1. Firebase Realtime Database

Database: `https://virtuoso-drive.firebaseio.com` (line 235). SDK: Firebase JS 6.1.0. No authentication is sent with any call.

### 1.1 Data model

```
/                                   database root (nothing else is written by the code)
└── All                             root folder content node (line 5)
    ├── <pushKey>                   file record
    │     name: "Lista 1.pdf"
    │     type: "application/pdf"
    │     path: "All/Lista 1.pdf"
    │     size: 123456
    ├── <pushKey>                   folder record
    │     name: "Circuitos"
    │     type: "folder"
    │     path: "All"
    └── Circuitos                   content node of the folder named "Circuitos"
        ├── <pushKey>               file record, path: "All/Circuitos/<original file name>"
        ├── <pushKey>               folder record, path: "All/Circuitos"
        └── <sub-folder name>       content node of that sub-folder
```

The names and values above are illustrative; the live data was not inspected.

**File record** (written at lines 363-368, rewritten at line 426)

| Field | Type | Source | Meaning |
|---|---|---|---|
| `name` | string | Storage metadata `name` at upload; replaced by rename | Displayed name. After a rename it differs from the stored object's name |
| `type` | string | Storage metadata `contentType` | Content type, used only to choose the icon. Any value other than `"folder"` means file. Whether it can be missing for a file the browser could not type was not verified |
| `path` | string | Storage metadata `fullPath` | Storage object key: `<folder path>/<original file name>`. Never changed after upload. The only link from the record to the file contents |
| `size` | number | Storage metadata `size` | Bytes |

**Folder record** (written at lines 472-476)

| Field | Type | Meaning |
|---|---|---|
| `name` | string | Displayed name, and the key of the folder's content node |
| `type` | string | Always `"folder"` |
| `path` | string | Path of the **parent** folder, for example `"All"`. Not the folder's own path. It is written but never read for folders, except that the download and duplicate-check code reads `path` of every record without checking the type (lines 488, 538) |

No `size` on folders. No other fields exist on either record: no identifier other than the push key, no timestamps, no author, no checksum.

**Structural rules, as the code applies them**

- A folder's content node sits beside the records of its parent, under a key equal to the folder's displayed name. Records are told apart from content nodes only by having a truthy `type` (line 685; also lines 258, 274, 325).
- Push keys are generated by the client SDK and sort by creation time; that is the display order **(inference: documented push-key behaviour)**.
- A folder with nothing in it has a record and no content node **(inference: the database keeps no empty nodes)**.
- The folder's own address is not stored anywhere; it is rebuilt from the chain of names the visitor walked (`currentFolder`).
- Nothing enforces unique names, valid characters, or that a `path` points at an existing object.

### 1.2 Operations

All go through `getFirebaseRef(path)` (lines 637-643): `firebase.database().ref(path)`, with `path` defaulting to `currentFolder.join('/')`.

| Id | Business operation | SDK call | Path | Payload or result | Lines |
|---|---|---|---|---|---|
| DB-1 | Browse and live refresh | `on('value', cb)` | current folder | Full subtree of the folder on attach and on every change at or below it. Children with a truthy `type` are drawn in key order | 676-691 |
| DB-2 | Leave a folder | `off('value')` | previous folder | Detaches every `value` listener at that path | 647 |
| DB-3 | Upload: duplicate check | `once('value', cb)` | current folder | Rejects the upload if any child's `path` equals `<folder path>/<file name>`. Not awaited before the upload starts (DEF-01) | 531-547 |
| DB-4 | Upload: create file record | `push().set(obj)` | folder open when the upload finishes (DEF-03) | `{name, type, path, size}` | 363-368 |
| DB-5 | Create folder | `push().set(obj)` | current folder | `{name, type: 'folder', path: <current folder path>}` | 472-476 |
| DB-6 | Rename file | `child(key).set(obj)` | `<current folder>/<key>` | The record read back from the row, with `name` replaced | 426 |
| DB-7 | Delete: remove record | `child(key).remove()` | `<folder open when the delete finishes>/<key>` | none | 451 |
| DB-8 | Delete folder: read content | `on('value', cb)` then `off('value')` | `<parent path>/<folder name>` | Subtree of the folder | 249-295 |
| DB-9 | Delete folder: remove content | `remove()` | `<parent path>/<folder name>` | Removes the whole content node, sub-folders included | 294 |

None of the write calls checks its result; a failed write is not noticed or reported.

## 2. Cloud Storage for Firebase

Bucket: `virtuoso-drive.appspot.com` (line 237). No authentication is sent.

### 2.1 Object layout

- Object key: `<folder path>/<file name at upload>`, for example `All/Circuitos/Lista 1.pdf` (line 549). The folder path is the same chain of names used in the database.
- The key is fixed at upload. Rename does not move or copy the object.
- Content type and size are whatever the SDK and service record at upload; the application sets no metadata of its own (line 551, `put(file)` with no metadata argument).
- Folders have no object or marker in storage.
- Uploading to an existing key replaces the object (DEF-01).

### 2.2 Operations

| Id | Business operation | SDK call | Object | Result | Lines |
|---|---|---|---|---|---|
| ST-1 | Upload | `ref(<folder path>).child(<file name>).put(file)` with `task.on('state_changed', progress, error, complete)` | `<folder path>/<file name>` | Progress events `bytesTransferred`, `totalBytes` | 549-567 |
| ST-2 | Upload: read metadata | `fileRef.getMetadata()` | same | `name`, `contentType`, `fullPath`, `size` are copied into the file record | 569-577 |
| ST-3 | Open file | `ref(file.path).getDownloadURL()` then `window.open(url)` | record `path` | Opens the URL in a new window | 162-170 |
| ST-4 | Download | `ref(file.path).getDownloadURL()` then `XMLHttpRequest` GET with `responseType = 'blob'`, saved through a temporary link with `download = <displayed name>` | record `path` | File saved under the displayed name | 488-506, 514-521 |
| ST-5 | Delete file | `ref(<current folder path>).child(<last segment of file.path>).delete()` | rebuilt from the open folder, not taken from `path` | none | 32-38, 327-329 |
| ST-6 | Delete file inside a deleted folder | `ref(<folder path>).child(<record displayed name>).delete()` | rebuilt from the displayed name (DEF-08) | none | 276 |

Notes:

- A download URL from this SDK is a long-lived link that anyone can use **(inference: documented platform behaviour)**.
- ST-4 reads the file from another origin with XHR, which needs cross-origin access configured on the bucket. That configuration is not in the repository **(inference)**.

## 3. Security Rules

`app/database.rules.json` (complete file):

```json
{
  "rules": {
    ".read": true,
    ".write": true
  }
}
```

`app/storage.rules` (complete file):

```
service firebase.storage {
  match /b/{bucket}/o {
    match /{allPaths=**} {
      allow read, write;
    }
  }
}
```

Effect: any client on the internet that knows the project identifiers (published in the page source, lines 232-240) can read, create, overwrite and delete every database node, including nodes outside `All`, and every stored object. There is no validation rule, no size limit, no content-type rule and no index definition. These are the rules in the repository; whether the deployed rules are the same was not checked. See SEC-01 and SEC-02.
