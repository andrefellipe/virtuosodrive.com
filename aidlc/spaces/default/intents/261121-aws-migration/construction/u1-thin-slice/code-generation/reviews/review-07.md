### Answers to the questions

**1. Safety of the live databases.** I traced every reference. The copy reads `aws_db_instance.this` only for `identifier`, `engine` and `instance_class`, and the parameter group and subnet group only for their names. Nothing in `this`, the parameter group, the subnet group or the secret refers to the copy or the two variables. Setting a moment, setting use, clearing use, removing the moment, or changing the moment can only add, change or delete `aws_db_instance.restored[0]` and its log group. `prevent_destroy` stays on `this`. The Lambda functions and IAM policies are the only existing resources that change, and only with the switches. No finding.

**2. Production's plan.** With both defaults, production's plan has no change from this diff. The `Resource` value goes in as a one-element list, becomes one string, and `jsondecode(jsonencode("arn..."))` returns that same string, so the rendered policy JSON is identical. The conditional's two branches are both `string`, so the types are valid. With an unknown `resource_id` the whole value is unknown, which is only the case in a new environment, as before. `one(aws_db_instance.restored)` on an empty tuple yields a null of dynamic type, which unifies with the object type. The mock-provider tests do cover the `count = 0` shape, and the real plan has the same shape. The new module outputs (`database_hosts`, `database_sign_in`, `sign_in_resource_ids`) are not root outputs, so they add nothing to production's plan. The one output that can fail on a missing state attribute is `restored_copy` (finding above).

**3. Will the restore work with provider 6.74.0.** As far as I know, yes. `restore_to_point_in_time` with `source_db_instance_identifier` and `restore_time` is a supported form. The omitted `allocated_storage`, `username`, `db_name` and `password` are exactly what a restore must not set. `storage_encrypted = true` matches the source, so no replacement follows. `skip_final_snapshot = true` and `delete_automated_backups = true` make the destroy clean. The log group is declared and the instance depends on it, so RDS does not create it first. Unsure, and only a real run settles it: whether `ca_cert_identifier`, `backup_window` and `maintenance_window` are applied in the restore call or by a later modify, and whether a later plan shows drift (finding above).

**4. The test identity's permissions.** The boundary allows `rds:*` and `logs:*` with no resource limit. `rds:RestoreDBInstanceToPointInTime`, creating and deleting `vd-test-db-restored`, creating the log group and `iam:PutRolePolicy` on `vd-test-*` roles (with the boundary condition the roles already carry) are all covered. Nothing named is missing. One unknown: the boundary has no `kms:*`. The copy is encrypted with the same service-owned key as the source, and the original was created by the same identity, so this should pass, but it is untested for a restore.

**5. Timing.** See the second finding. It is plausible but not certain that the first restore fits. The credentials expire at 60 minutes after the identity step, with the restore early in the run, so the credentials are the lesser risk and the 60-minute job limit is the greater.

**6. Pointing at the copy.** `DB_HOST` is set from `module.database.address` in both functions (`infra/modules/server/main.tf` lines 312 and 375). A change reaches `$LATEST` in the apply. The `live` alias has `function_version` in `ignore_changes`, so the alias moves only in the deploy's switch step, which calls `update-function-code` and `publish-version` from `$LATEST`. The new version therefore carries the new address in the same run. The change runner is published from `$LATEST` too (`update-function-code --publish`), so it runs against the copy. The copy already has `pgmigrations` with 0001 and both database users, so it applies nothing and does not touch the master secret. The TLS check passes: both clients use the regional RDS bundle with `rejectUnauthorized: true`, and the copy's certificate comes from the same authority and names its own host. The database security group admits both functions by group reference, which applies to every instance using the group.

**7. Go back after switching.** The developer's warning is correct: each published version keeps the `DB_HOST` it had when published. Procedure 4's final bullet is sufficient for the normal two-pull-request path. See the first finding for the case it does not cover.

**8. The workflow.** The branch check runs before the identity is taken, and the test role's trust policy requires `refs/heads/aws-migration`, so another branch is stopped twice. There is no `pull_request` trigger, so a pull request or fork cannot start it, and the default branch is `aws-migration` (`infra/setup/github-settings.sh`). The action is pinned to the same commit as `deliver.yml`. Each attempt is refused for the intended reason. The fallback trust document equals `identities.tf` (federated principal, `AssumeRoleWithWebIdentity`, `aud` and `sub` as `StringEquals`, no other condition), provided `github_repository` and `integration_branch` keep their defaults. `GITHUB_REPOSITORY` equals the default. It is also harmless if allowed only if that equality holds. The answer is never printed, and only the `kind` is extracted. The account number is masked. No leak found. The one weakness is the classifier (finding above).

**9. `alarms` and `forced_failure` in test.** They create the Route 53 health check on `/v1/health`, the health and error-rate alarms and the dashboard widget, and switch on `GET /v1/forced-failure` in the server. The gate covers `/v1/*`, so only someone with the password reaches it. Nothing in the smoke check, the end-to-end tests or the measurement refers to it. The error-rate alarm needs 20 requests and more than 5% failures, so a normal run does not trip it. The same module is already proven in production. Unprovable: whether the two alarms stay quiet through a real run of the 48 end-to-end tests.

**10. Checkov.** The inline skips match rule for rule: `CKV_AWS_157`, `118`, `353`, `354`, `293`, `CKV2_AWS_60` on the instance, and `CKV_AWS_158` and `338` on the log group, the same set `aws_db_instance.this` and its log group carry. The restored instance sets the same encryption, IAM authentication, private access, backup retention, minor-version upgrade, log export and certificate settings, so I found no rule it should trip that `this` does not. Not verified by running Checkov (not installed here), and I cannot say how it parses `jsondecode` in the IAM policy's `Resource`.

**11. The tests.** See the fifth finding.

**12. The records.** I found no email address and no account number. `going-back.md` shows the repository's GitHub URL with the owner's handle (also in `infra/setup/variables.tf`, so not new). The arithmetic checks out: 04:31:50 to 04:32:24 is 34 seconds, 04:32:49 to 04:33:13 is 24, and 75,321 bytes is about 74 KB. The records say plainly what was not looked at.

### Outside this change

**Question 13: confirmed, and serious.** `db-migrate/src/runner.integration.test.ts` lines 66-69 expect `applied` to equal exactly `["0001_site-information"]`, and `db-migrate/src/migrations.integration.test.ts` lines 35 and 43 expect `firstRun` and the recorded names to equal `[FIRST_CHANGE]`. The `code` job in `.github/workflows/checks.yml` ("Compatibility with every version in reach") copies the pull request's `db-migrate/migrations` into a checkout of the production Release and runs that Release's own tests. Those tests are frozen at that commit, so they can never accept a second migration file. The pull request author cannot fix it by editing tests in their own pull request. Any pull request adding a file under `db-migrate/migrations/` fails the `code` check, which blocks the merge. For the next Unit that adds a table (accounts, browsing), schema changes are blocked until the check or the tests stop asserting the full list. The plan's own failing-migration rehearsal (`0002_rehearsal-fails.sql`, Step 19) hits the same wall. Not counted against this change.

The change cannot alter or destroy the live databases, production's plan is unchanged with the defaults, and the Terraform, the workflow and the checks I could run all hold up; what remains are operating risks and wording. The first real restore is the point where several things only a real run can show (certificate, windows and drift, job time) will be seen.
