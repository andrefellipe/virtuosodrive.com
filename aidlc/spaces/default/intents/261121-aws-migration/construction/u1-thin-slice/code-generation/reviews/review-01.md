### What I checked and found sound

- **Server request steps.** The origin secret is checked first with a constant-time comparison on hashed values. One re-read follows a mismatch, at most once a minute, and it keeps the held value if the re-read fails. The 3-second deadline covers connect plus statement, with a 2-second connect limit. One connection is kept per running copy and dropped on any failure. TLS uses `rejectUnauthorized` with the RDS bundle and TLS 1.2 or later. The IAM token is made locally with no network call. Problems carry a code and nothing internal. Log entries are scrubbed for email shapes.
- **Access gate.** The comparison is constant-time over SHA-256 values. A malformed stored hash refuses everything. Only the exact `/v1/health` path bypasses it. The cookie is `Secure; SameSite=Strict`. The password page's script and style are pinned in its CSP by hash. The built file is exercised in a `vm` context in `scripts/src/commands.test.ts` (a global `handler`, size limit, both placeholders present once).
- **Change runner.** Users are created only when the migrator sign-in is refused and the master login confirms that neither user exists. A half-present state stops with a message. node-pg-migrate takes its lock and applies each file once. The integration tests run against a real PostgreSQL 18.1 with TLS. The SQL grants are minimal. The built package holds `migrations/` and `certs/` where `paths.ts` and `index.ts` look for them.
- **Network and data.** No NAT, no internet gateway, one Secrets Manager endpoint with a policy limited to the environment's own secrets. The database is private, encrypted, with `rds.force_ssl` and IAM sign-in. Security group rules are paired and narrow.
- **Workflows.** `checks` has no `id-token`. Actions are pinned by commit. The `deliver` order is infrastructure, database, server, page (entry document last), with the old alias and entry document restored if the switch fails. The first deployment skips the smoke check against the placeholder. Production needs approval and its own identity. The page build uses a `/r/<version>/` base, so going back finds the old files.
- **Tests.** No skipped, todo or trivially true assertions found. The database is never mocked in integration tests. Only AWS SDK calls are replaced at the boundary.
- **Deviations 1 to 20 in the summary.** Each is acceptable as written. The unencrypted alarm topic is a reasoned Checkov exception.

### What I could not check

- Whether AWS accepts the IAM conditions (tag, route 53 record name), whether Budgets accepts a forecast notification and a topic without a policy, and whether RDS offers PostgreSQL 18 with parameter family `postgres18`. None of this can be run without an account.
- Whether the commit hashes in the workflows resolve to the versions named in the comments, and whether Checkov raises further findings (it is not installed here).
- The CloudFront Functions runtime itself, the log group name for the gate, and the empty `environment:` expression in `go-back.yml` and `compare.yml`.
- The end-to-end tests (not run, as instructed) and the setup scripts (not run, as instructed).

### Summary

The server, gate, change runner, tests and workflows are well built and verified here. The setup folder is where the first run will break. The budget filter is mis-escaped, so the budget alarm would never count anything. A failed first run cannot be resumed with the script. The pipeline's failure notices are blocked by its own tag Deny. Fix the Critical and the three Major findings, then re-review.
