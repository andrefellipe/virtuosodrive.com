## S1. The access password (NFR2.2 to NFR2.5)

The maintainer chose a password page of the site's own (Q1).

**What is stored where.**

- The password: 32 random letters and digits, generated by Terraform for each environment and written to the secrets service. The maintainer reads it there once per device.
- At the edge: only a one-way scramble (SHA-256) of the password, placed in the edge check when it is deployed. Reading the edge check's code does not reveal the password.
- On a device: the password itself, in a cookie named `vd_access`, marked Secure and SameSite=Strict, lasting 30 days. It is a cookie, not the `Authorization` header, so it never collides with the session contract C1 defines.

**The check, on every request at the edge.**

1. If the path is `/v1/health`, let it through.
2. If the request carries `vd_access` and its scramble equals the stored scramble (compared in constant time), let it through.
3. Otherwise answer with status 401 and the password page, and write one log line with the operation "access refused".

**The password page.** One small self-contained page with one field. On
submit, a script on the page stores what was typed in the cookie and reloads.
A wrong password therefore simply shows the page again. The page loads nothing
from elsewhere and has no other script.

**Turning it off.** One setting per environment, changed through the pipeline
like any other change. Off means the edge check lets everything through.
Production's is switched off at the switch (U9); the test environment's stays
on.

**Replacing the password.** Changing a version marker in the Terraform
definitions makes Terraform generate a new password, store it, and redeploy
the edge check with the new scramble. Every device is asked again.

**The pipeline's tests** read the password from the secrets service with the
environment's identity and set the cookie before opening the page.

**Why the cookie cannot be marked unreadable by scripts.** It is set by the
password page's own script, so it cannot be HttpOnly. The page's content
security policy (S5) allows no script but the site's own, which is the
protection against another script reading it. Accepted for a password that
guards nothing sensitive in this Unit; revisited if that changes.

**Guessing.** No counting of wrong attempts (NFR2.3). Guesses are made against
the edge, which has no request limit, so the server's limit plays no part
here; the requirement's reasoning on that point was wrong. What makes guessing
infeasible is size alone: 32 characters from 62 give about 10 to the power 57
possibilities, out of reach at any request rate the edge could serve.

**When the cookie is missing or wrong on a call to the server.** The edge
answers 401 with the password page, which is not a Problem. The page's shared
call function (performance design, P5) treats a 401 that is not a Problem as
"access needed" and reloads the page, which then shows the password page. It
does not retry.

## S2. The server cannot be reached around the edge (NFR2.2)

The server's entry point has its own public address, as that service always
does. To make the edge the only way in:

- The edge adds a header carrying a second secret (generated per environment, held in the secrets service) to every request it forwards to the server.
- The server's first act on every request, before choosing an operation, is to compare that header with the value it holds, in constant time. A request without it is answered 403 with no body and logged as "access refused".
- The health check is not exempt from this: the health monitor asks through the edge.

## S3. Pipeline identities (NFR15.1, NFR15.2, NFR15.13)

| Identity | Who can take it | What it can do |
|----------|-----------------|----------------|
| None | A pull request's checks | Nothing in AWS. They need no AWS access (S8) |
| Test | A workflow of this repository running on the branch `aws-migration` | Create and change resources named for the test environment; read and write the test environment's state; read the test environment's secrets |
| Production | A job of this repository running in the GitHub environment `production`, which starts only after the maintainer approves | The same, for production |

- The trust for each identity names the repository and, respectively, the branch and the environment, as the conditions on the token GitHub issues. No other workflow, branch, fork or repository satisfies them. The exact form of those conditions is to confirm against GitHub's and AWS's documentation.
- Credentials last one hour at most.
- The production trust is further narrowed on GitHub's side: the `production` environment accepts jobs only from the branch `aws-migration`, so a job on another branch cannot enter it even with approval.
- **One outer limit per environment** (a permissions boundary each, made by the setup): one for test, one for production. Each allows action only on resources whose names begin with its own environment's prefix, on its own path in the state bucket, and on its own environment's secrets, and denies everything of the other environment. Each also denies any change to: the budget alarm, the notification channel, both identities and their trust, both outer limits, and the state bucket's settings.
- **Roles the pipeline creates** (the server's and the change runner's) must be named with the environment's prefix and must carry that same environment's outer limit; the identity is denied creating a role without it, and denied handing any role to a service unless the role has its environment's prefix. So nothing the test identity can create or hand over can reach production, and the pipeline cannot make itself a stronger identity.

### The server's and the change runner's own identities (NFR15.3)

| Identity | May | May not |
|----------|-----|---------|
| Server | Connect to its environment's database as an ordinary user that can read and write rows but not change the structure; read the secrets it needs (the edge-to-server secret and, if any, its database credentials); write to its own log group | Anything else. No wildcard in its permissions |
| Change runner | Connect to its environment's database as the owner of the structure; read its database credentials if any; write to its own log group | Be called by anything but the pipeline's identity for that environment |

The two database users are different, so a flaw in an operation cannot alter
or drop a table.

**Checked once, and recorded:** from the test identity, an attempt to change a
production resource, the budget alarm, and a trust definition; each must be
refused. From a pull request, an attempt to take either identity must be
refused.

## S4. Secrets (NFR15.4, NFR15.5, NFR5.1)

| Secret | Made by | Held in | Read by |
|--------|---------|---------|---------|
| Access password | Terraform, per environment | Secrets service | The maintainer; the pipeline's tests |
| Its scramble | Terraform, derived | The edge check's deployed code | The edge check |
| Edge-to-server secret | Terraform, per environment | Secrets service | The edge (as a header it adds); the server |
| Database credentials | Depends on the service chosen | Secrets service, or none if the service allows sign-in by the server's own identity | The server; the change runner |
| Maintainer's email address | Typed at setup | The notification channel only | Nobody else; alarms name the channel |

- No secret is in the repository, in a Terraform variables file, in the page's files, or printed by the pipeline. A secret scanner runs in the pull request.
- **Secrets in Terraform's state.** Values Terraform generates are recorded in its state. The state is therefore treated as secret: encrypted, one state per environment, readable only by that environment's identity and the maintainer (NFR15.5). This settles the requirements' open point: the state is not kept free of secrets; it is protected as one.
- **How the server gets its values.** The requirement says the server reads them from the secrets service when it starts. From a network with no route to the internet, that needs a private connection point with a fixed monthly cost. Infrastructure Design chooses between that and handing the values to the server when it is deployed (encrypted in its configuration), under three conditions: the value is never in the repository or the pipeline's output; replacing it needs no code change; and the choice is named in the cost estimate. If the second is chosen it departs from the letter of NFR15.4 ("read by the server when it starts") and is put to the maintainer there.
- **Preference for no database password at all.** If the chosen database service lets the server sign in with its own identity, that is used, and no database password exists.

## S5. What the browser is told (NFR1.3, NFR3.4, NFR4.2)

Sent with the page and with the password page, by the edge:

| Header | Value, in substance | Why |
|--------|---------------------|-----|
| Content-Security-Policy | Everything from the site's own address only; no inline script except the password page's one script, allowed by its fingerprint; no framing by other sites | No script, style, font or request to anywhere else, Google included |
| Strict-Transport-Security | One year | The browser never tries plain HTTP again |
| X-Content-Type-Options | nosniff | Files are treated as the type declared |
| Referrer-Policy | same-origin | The address is not leaked to other sites |
| Cache-Control | Per `performance-design.md` | The entry document is never stored |

Server answers carry `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.

The edge accepts TLS 1.2 or later only and redirects plain HTTP to HTTPS. The
edge speaks to the server's entry point and the files store over TLS. The
server connects to the database over TLS and verifies its certificate against
the authority the database service publishes (NFR4.3).

## S6. Requests into the server (NFR3.1, NFR3.2, NFR3.3, NFR3.5, NFR2.1)

Every request passes through the same steps in the same order, written once
and shared by all operations. Later Units add operations, not steps.

1. Verify the edge's secret (S2).
2. Take the request identifier if it is well formed, else make one (rules BR1.4).
3. Find the operation. No match: `notFound`.
4. Validate what the operation reads from the request against its declared shape (Zod). Failure: `invalidInput`. Unknown query parameters are refused, not ignored.
5. Run the operation.
6. Turn any failure into a Problem (contract C1) that carries a code and nothing internal. The internal reason goes to the log entry only.
7. Write the log entry (see `observability-design.md`).

- Operations are declared in one list, each with its method, path and shapes. A test reads the list and fails if any operation of this Unit accepts a method other than GET (NFR2.1). The same list is what the OpenAPI description is checked against.
- Database statements are written with placeholders and values passed separately. A lint rule forbids building a statement from a template with values in it.

## S7. The page (NFR3.4, NFR1.1, NFR1.2)

- React escapes text by default. The one way around it (`dangerouslySetInnerHTML`) is forbidden by a lint rule.
- The dependency list and the built files are searched for Firebase and Google libraries in the pull request.
- The end-to-end test records every address the page contacts and fails on any but the site's own.

## S8. The pull request's checks need no AWS access (NFR15.2, NFR15.6, NFR15.7, NFR13.1)

| Check | Needs |
|-------|-------|
| Lint, format, type check | Nothing |
| Unit tests; integration tests with a real PostgreSQL in a container | Nothing outside the runner |
| Coverage threshold | Nothing |
| Terraform format check and validation | Nothing (no state, no identity) |
| Checkov on the Terraform files | Nothing |
| Dependency audit; secret scanner; search for Firebase and for email addresses | Nothing |
| The pull request's description names its Unit | Nothing |
| Pinning: lockfile present and unchanged by install; Terraform and providers at exact versions; actions referenced by commit | Nothing |

Workflows triggered by pull requests are given no permission to request an
AWS token. Terraform's plan, which needs the state, runs after the merge under
the environment's identity, and its output is shown in the pipeline's run
before it is applied; what is applied is exactly the plan that was shown.

**What the maintainer sees before approving production.** The production plan
can only be made with the production identity, which exists only after
approval. So the approval is given on the strength of the same definitions
having just been planned and applied in the test environment, whose plan the
maintainer can read. The production plan is then shown in the run and applied
unchanged. A production plan that differs from the test one in kind (not just
in names) is something this design does not stop; the maintainer can cancel
the run on seeing it, during a pause of two minutes between showing and
applying.

**Branch protection (NFR13.1).** The branch `aws-migration` is protected on
GitHub: no direct pushes, by anyone including administrators; a pull request
is required; the checks in the table above are required to pass; and the
branch must be up to date before merging. These settings are themselves
defined in the repository and applied by the setup where GitHub's plan for
the repository allows it; if it does not, that is reported to the maintainer
as a gap, since nothing else can enforce it.

## S9. Encryption at rest (NFR4.1)

Every store is encrypted with the service's own managed keys: the database and
its backups, both buckets, the logs, the secrets. Keys managed by the
maintainer are not used: each has a fixed monthly cost and nothing here
requires them. Where Checkov's defaults ask for them, the exception is
recorded in the repository with this reason.

## S10. Logs (NFR5.2, NFR5.3)

What may be in an entry is covered in `observability-design.md`: entries are
built from named fields only, and an email-shaped value in any text field is
replaced before writing.

**Who may read them (NFR5.3).** Log groups carry the environment's prefix.
They can be read by the maintainer's own AWS sign-in and by the alarms and
saved searches defined for that environment. The pipeline's identities can
create and configure log groups but are given no permission to read entries;
the server and the change runner can write to their own group and read none.
Nothing else in the account has access.

## Requirements this design leaves to a later Unit

None of this Unit's. Sign-in, sessions and authorisation of changes arrive with
U2 and are designed there; the steps in S6 leave a place for "who is asking"
between steps 3 and 4.

## Open points

1. **The edge check's abilities** (read a cookie, compute SHA-256, answer with a page, log a line, compare in constant time) are assumed of a small edge function and are to confirm. If one is missing, the fallback is a heavier kind of edge function, to be costed.
2. **The edge check must be written in JavaScript to run at the edge.** It is written in TypeScript and compiled; the compiled file is a build product, not a source file, so the project's rule against new plain JavaScript source files is kept.
3. **The password in a cookie readable by the site's own scripts** is a deliberate simplification (S1).
4. **Checkov exceptions** (S9, and any other) are each recorded with a reason; an unexplained one fails the pull request.
5. **The exact trust conditions for the two identities** are to confirm against current documentation before the setup is written.
