### Why, where it is not obvious

**T22, no routing library.** The page has one kind of address. A library
would be the largest thing in the bundle for the smallest job, and needs
approval. If U2's sign-in screens or the maintainer's screens need more, a
library is proposed then.

**T24, one table.** The order of a folder's list, its set of names and the
identifier of a row all span folders and files. With two tables each of those
needs something extra to hold across both; with one, each is a single
constraint. The price is that a few columns apply to files only (size,
content type, contents, the reason for deletion), which checks in the
database keep empty for folders.

**T25, random identifiers.** A time-ordered identifier would be slightly
kinder to the database's index, but it would show when an item was made and
let neighbours be guessed. At this size the index cost is nothing.

**T26, one place for name comparison.** Case folding and composed forms are
implemented slightly differently by JavaScript and by PostgreSQL. If the
check ran in one and the constraint in the other, a name could pass the check
and be refused by the store, or two look-alike names could both be stored.
PostgreSQL's own functions for normal form and for case are used for both.
The comparison required is fixed by the table "Name cases" in
`security-requirements.md`: one composed form, and case compared one
character to one character. Which functions give exactly those fifteen
results on the installed version is found at the next step, by running the
table. There is no fallback that changes a result: if no arrangement in the
database gives all fifteen, the question comes back to the maintainer before
anything is built.

**T28, a row lock.** It makes changes to one folder queue without touching
other folders, and readers do not wait for it. The alternative, letting two
changes run and retrying the loser, needs every later Unit to write a retry
correctly.
