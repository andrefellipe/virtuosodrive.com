# Security Design: U3, browsing and selecting

How the security requirements are met.

Sources: `security-requirements.md` and `tech-stack-decisions.md` in
`aidlc/spaces/default/intents/261121-aws-migration/construction/u3-browsing/nfr-requirements/`,
U3's design
(`aidlc/spaces/default/intents/261121-aws-migration/construction/u3-browsing/functional-design/functional-spec.md`),
and contracts C1, C3 and C9
(`aidlc/spaces/default/intents/261121-aws-migration/inception/contract-design/contract-summary.md`).
U1's mechanisms S1 to S10 still apply: the access password at the edge, the
secret that proves a request came through the edge, TLS everywhere, the
pipeline's identities, pinned dependencies and the scans. U3's are numbered
from S20. Several of them need changes to parts U1 built; those are listed
once, in `logical-components.md` under "Changes to what U1 built", and
referred to here by number.

## S20. The folder identifier is recognised before anything else

- One function decides what a folder identifier is: the text `root`, or exactly the 36-character lower-case form the database generates. Anything else, including the same identifier in upper case, an empty value, or a longer text, is "no such folder".
- It runs as the operation's declared check of its path value, before the operation runs, so a value that fails never reaches a statement. U1's request steps check only the query and know no path values; they are extended to hand an operation the named parts of its path (`logical-components.md`, changes 1 and 2).
- A malformed identifier gives the same "not found" answer as any other (S24), not `invalidInput`: the answer must not teach what identifiers look like. U1's steps always answer a failed check with `invalidInput`; they are extended so that an operation may declare "not found" for its path values (change 3). The default for every other operation stays as it is.
- The value sent is never logged (O20).

Meets NFR3.20.

## S21. The version a caller holds

- The server issues the version as a quoted text made of the folder's identifier and its version number.
- On the way in, the header is read only if it is 128 characters or fewer. A leading weak marker, which a part on the way may add when it changes the encoding, is removed. What remains must be exactly a version this server could have issued for the folder being asked about; if not, the caller is treated as holding none.
- A list of several versions in the header is not supported; it is treated as holding none.
- Three things U1 built must change for any of this to work (`logical-components.md`): the edge must pass the header to the server (change 8; today it is dropped); an operation must be able to read a header it declares (change 2); and it must be able to answer with a header and with no body (change 4).

Meets NFR3.21. An end-to-end test asks twice through the whole path and gets
"unchanged" the second time; that test is what proves the edge and the entry
point pass the header in both directions (see `logical-components.md`, open
point 2).

## S22. Identifiers

Generated by the database when the row is created, at random (verified:
version-4 form). No operation, and not the loader, supplies one. The server's
user cannot write to the table at all (S25).

Meets NFR2.24.

## S23. One module for names, one place for sameness

- **Normalising and validating** (rules BR2.4, BR2.5, BR2.7) is one module in Drive: compose, trim white space, count code points, refuse control and invisible formatting characters, "/", "." and "..". The module turns what a person typed into a name that may be stored, and gives the right code when it cannot.
- **The store refuses the same things itself.** Five checks on the name column refuse a name that is not composed, is empty or over 255 characters, is "." or "..", holds a forbidden character, or has white space at either end (verified; see `logical-components.md`). So a write that went round the module, by a fault in a later Unit, is refused, not stored.
- **One list.** Which characters are white space and which are invisible formatting characters is one data file in the repository, taken from Unicode's own tables. The module's patterns and the database's checks are both generated from it, and a test runs every listed character through both.
- **Sameness** (rule BR2.6) is decided by the database alone: the `name_key` column is derived by the database from the stored name, and the unique index is on it. The name check asks the database "is there an item not deleted in this folder whose key equals the key of this text", passing the text as a parameter and letting the database fold it. No code outside the database ever folds case.
- All fifteen cases of the "Name cases" table are tested twice, as the requirement says: through the name check, and as direct writes to the table, which must refuse or accept each one as the table lists. For a direct write "stored as" a trimmed or composed form means the untrimmed or uncomposed form is refused; only the module rewrites a name.

Meets NFR3.24. Binding on U6, U7 and U8: they call this module and write
through the change step (reliability design R21); none compares names itself.

## S24. An answer is built from a list of fields, never from a row

- The folder answer is assembled by a function that names each field it puts in: for the folder, its identifier, name and path; for a row, identifier, kind, name, and for a file size and content type. A column added to the table later does not appear in an answer by itself.
- One function makes the "not found" answer, and it is the only way the folder operation says not found: unknown, deleted, inside a deleted folder, or malformed. It takes no argument that could vary the answer.
- The statement that reads items states "not deleted" itself; there is no step afterwards that filters, so a hidden item is never in the server's hands when it builds an answer.

Meets NFR3.26, NFR3.27. The test compares the four not-found answers byte
for byte apart from the request identifier, with and without a version sent,
and asserts the exact set of fields of a full answer for a folder that also
holds deleted items. Binding on later Units: a field is added by changing the
function and the test's list in the same pull request.

## S25. The server cannot change content, whatever its code says

- In U3 the database user the server signs in as (`app`) is given only the right to read `items`, by the same change file that creates the table. A route that tried to write would be refused by the database.
- The change step and the name operations are not referenced by any operation in the server's list. The only caller is the sample loader, which is a mode of the change runner: a different function, started only by the pipeline, already signing in as the user that owns the tables (`migrator`). The server's function has no permission to sign in as that user (U1).
- The existing test over the server's list of operations still requires every one to be a GET.

Meets NFR2.20, NFR2.21. Binding on U6 and U7: the right to write is given to
the server's user in the Unit that adds the first change route, together
with the check of who is asking (contract C8), not before.

## S26. Damaged data cannot hold a request

The walk towards the top stops at 64 levels. Reaching the limit without
reaching the top is a fault: the request fails as a server error, and the
entry says which folder (O22). U1's 3-second limit on everything asked of the
database bounds the time in any case.

Meets NFR3.25.

## S27. "Unchanged" only for a folder that can still be seen

When a caller sends a version, the first statement is the walk (performance
design P20), and it reports whether the folder or anything above it is
deleted. That is checked before the versions are compared. So a caller
holding the current version of a folder whose grandparent has just been
deleted is told "not found".

Meets NFR3.28. Binding on U5 and U6: the order "visible first, then compare"
is in one function they do not reimplement.

## S28. Folder answers are not kept on the way

- Every answer of the folder operation, including "not found" and "unchanged", carries the instruction not to store it.
- The edge is configured, for everything under `/v1`, to keep nothing and to pass each request to the server. That is how U1 built it, and it covers this route as it stands.
- Setting the instruction needs an operation to be able to name response headers, which U1's operations cannot (`logical-components.md`, change 4).
- The page keeps the version itself (performance design P23), so nothing depends on the browser's store.

Meets NFR2.25. Checked by an integration assertion on the header, an
end-to-end assertion through the whole path, and an end-to-end test in which
the loader's content differs between two requests. Because nothing in U3 can
change content through the site, that last test changes the sample folder by
a direct, test-only write made with the pipeline's identity in the test
environment; the infrastructure step says how, or the test moves to U6.

## S29. Names never reach the page as markup, an address, or a log

- React puts text into the page as text. The lint rule against its one escape hatch (U1) covers the new components. Names also go into the page's title, the status line and text alternatives through text properties only.
- Addresses carry identifiers only (design rule BR3.1).
- Logs: O20 and O23.

Meets NFR3.23, NFR5.20. The end-to-end test uses the three slash-free sample
names; a unit test of the list component is given the story's exact
`<b>x</b>` as a row's name.

## S30. Statements

Every statement U3 adds is a fixed text with numbered parameters, including
the walk. U1's lint rule against building statements from text applies to
the new module. Each has an integration test with a name containing a quote
and a fragment of a statement.

Meets NFR3.22.

## S31. The sample loader is fenced twice

- It is wired into the pipeline only for the test environment.
- It reads the environment's name from its own configuration and refuses to do anything when that is production, before opening a connection.
- It has no route; it cannot be reached from the internet.

Meets NFR2.22.

## S32. Reading stays open

The folder operation never looks at a session. An end-to-end test reads a
folder with no session and stays in the suite for good (binding on U2).
While the environments are private, the access password at the edge is what
keeps strangers out; this operation neither knows nor depends on it.

Meets NFR2.23.

## Carried without change

| Requirement | Why nothing new is needed |
|-------------|---------------------------|
| NFR1.20 | No library added; icons bundled; U1's searches and its end-to-end check of contacted addresses now also visit a folder |
| NFR4.20 | The table is in the same encrypted database, reached over the same verified connection |
| NFR5.21 | No personal data: the account columns are empty until U6 |
| NFR5.2, NFR11.3 (U1's) | The folder request is logged by U1's request log with its scrubbing, and counted against the entry point's one limit |

## Open points

1. **The test that a change shows at the next request (S28)** needs a way to change sample content in the test environment between two requests. If the infrastructure step finds none that is clean, the test is written in U6, where the site itself can change content.
2. **What the edge passes on.** Inwards, the caller's version header and the accepted encodings are dropped today and are added by change 8. Outwards, the version header and the encoding are expected to pass untouched because the edge keeps nothing for `/v1`; that is proven only by the end-to-end tests.
