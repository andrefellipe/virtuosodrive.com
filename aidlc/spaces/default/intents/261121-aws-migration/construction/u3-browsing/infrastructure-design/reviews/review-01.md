### Checked and found sound

- Claims in "Checked before writing this" that match U1's files: the gate rewrites paths with no dot outside `/v1` to `/index.html`; the `/v1/*` behaviour uses `Managed-CachingDisabled`; the server's origin request policy lists only `X-Request-Id`, `Accept` and `Content-Type`; the catch-all route `$default` and payload format 2.0 exist; the change runner has a 5-minute limit, concurrency of 1 and `VD_ENVIRONMENT`; the server function has 512 MB and 8 seconds; the deploy action's role can invoke the runner (the boundary allows `lambda:*`). U1's end-to-end test already proves `/folders/example` returns the entry document.
- The edge change: the origin request policy is the right place; nothing else at the edge blocks a 304 or an `ETag` (the server response headers policy sets only HSTS and nosniff; the gate only reads cookies and rewrites the path). With caching disabled the edge does not compress, so the server's `Content-Encoding` passes through. The policy updates in place, and `cloudfront:*` is in the boundary.
- Saved searches and the dashboard view need only `logs:PutQueryDefinition` and `cloudwatch:PutDashboard`, which the boundary allows (it denies only reading entries).
- Cost: nothing missed that is more than cents. CloudFront Function and API requests, log ingestion for the extra tests and the extra runner invocation are all negligible.
- Monitoring and the rules of the operation phase: a smoke test exists in production, no new component needs its own health or error metric, and the security effect of the edge change is stated.
- Open point 1's statement that stage 3 is skipped on a first deployment is correct for the deploy action as built.

### Could not check

- Whether CloudFront's API accepts `Accept-Encoding` in an origin request policy when the cache policy disables caching. The design cites AWS documentation; I could not open it. The failure would show as a failed apply in the test environment, not a silent fault.
- The N/A rows (about 25) and the U3 requirement text beyond the IDs quoted; I checked only that the OK targets exist, and a sample of the N/A rows.
- Whether the Terraform test framework can assert the policy header list without a plan against a real account.

### Summary

The design is right that U3 needs almost nothing new from AWS, and its checks of the edge hold. It is NOT-READY because the shared smoke check would fail stage 3 and go-back against a pre-U3 server, the folder-speed fallback needs a permission the pipeline is denied, and building on an undeployed U1 breaks the team's walking-skeleton rule without stating the consequences.
