### Other checks

**1. Does the code do what Step 18 says.** Yes. `acceptsGzip` is `value === "1"` and nothing else, so absent, empty, `0`, `true`, `1 `, `1,1` and `gzip` all give the plain answer; ten such values are tested. The other two conditions of P22 (over 1,024 bytes; compressed form as handed over is the smaller) are unchanged. I searched for `accept-encoding` in `server/src`, `web/src`, `scripts/src`, `edge/src`, `e2e`, `infra`, `docs` and `.github`: the server reads it nowhere. What remains is the comments that explain the change, the Terraform assertion that it must not be listed, the gate's `Accept-Encoding: identity` on its plain request, and tests that send it on purpose to show it changes nothing. The developer's table of these places is accurate. `enable_accept_encoding_gzip` and `_brotli` appear in the cache policy for the page's files (U1), not for `/v1`.

**2. The edge, and how sure I am that AWS accepts it.**
- The list is exactly `X-Request-Id`, `Accept`, `Content-Type`, `If-None-Match`, `X-Accept-Gzip` in `infra/modules/edge/main.tf`, and the Terraform test asserts it and the absence of `Accept-Encoding`.
- Confidence that AWS accepts a custom header there beside the managed caching-disabled cache policy: high, about 90%. Custom `X-` headers in an origin request policy whitelist are an ordinary use of the feature. The documented quota is 10 headers per policy; this uses 5.
- Confidence that AWS accepts `If-None-Match` in the same list: moderate to good, about 80%. What I read: the CloudFront developer guide page "Request and response behavior for custom origins" lists `If-None-Match` as a header CloudFront forwards, and as one that caching can be based on. The page on origin request policies sets no list of refused headers and says nothing of `Accept-Encoding` or `If-None-Match`. The quotas page has no such list either. So I could not find the documented rule that produced the first refusal; that is exactly the gap that made the first attempt fail. The only thing I can add is that the refusal named only `Accept-Encoding`. I do not know whether AWS validates the whole list and reports only the first bad entry or all bad entries. The developer says the same, and Step 18 has the remedy if it fails: the run stops at the same resource with nothing put in place.
- The browser's own `Accept-Encoding` is not passed on. CloudFront does not compress `/v1` itself: the cache policy is the managed caching-disabled one, with no gzip or brotli switch on, so it has no reason to touch the body. The docs' list of response headers CloudFront removes or replaces does not include `Content-Encoding` or `Content-Length`. So a gzip answer goes to the browser as the server sent it. The only callers that get gzip are those that sent `X-Accept-Gzip: 1`: the page (a browser, which reads gzip) and our own checks. A caller that cannot read gzip would have to send that header itself. Note that CloudFront may switch to chunked transfer and drop `Content-Length`; the gate allows for that.
- The CloudFront docs say the origin's `Vary` values other than a few are removed before the answer goes out, unless the header is forwarded and the origin names it, which is the case here. Either way it changes nothing, as every answer is `no-store`.

**3. `Vary`.** `Vary: X-Accept-Gzip` is on the 200 only, for a reason that holds: its body depends on the header. The four not-found answers were not touched and their byte-for-byte test still passes. The 304 has no `Vary` (see the second new finding).

**4. The page.**
- `readFolder` sends `X-Accept-Gzip: 1` on every attempt (a test covers three attempts of a retried call), with and without a held version.
- `readFromServer` for another path does not send it. A test covers that.
- A custom request header on a same-origin `fetch` does not cause a preflight: preflights belong to cross-origin requests. The page calls its own address.
- The access gate at the edge (`edge/src/gate.ts`) judges by path and cookie; its comment (line 190) says it looks at no header, and no step I found drops unknown headers. On the server, `request-steps.ts` hands an operation only the headers it declares, case-insensitively, and the API gateway merges duplicate headers with a comma, which the `1,1` test covers.
- U1's behaviour in `call-server.ts` is intact: the `heldVersion` argument became `options` and `attempt` reads `options.heldVersion`. The existing U1 cases pass without change. The one weakness is the first new finding.

**5. The gate "compressed through the whole path".**
- Node's `fetch` (undici) decodes the body but leaves the response headers as received, so `Content-Encoding: gzip` and the compressed `Content-Length` are still readable. I rely on my knowledge of undici here; I did not run a request against a server.
- The gate can fail when things are wrong: no gzip with the header gives a failure naming `none`; gzip without the header fails; if the edge removes the header, the server answers plain and the first request fails. If the edge strips `Content-Encoding` but leaves a gzip body, `response.json()` fails and the gate reports a failure through its guard. If the edge adds a `Content-Encoding` to the plain answer, the second request fails.
- It does not fail on correct behaviour: if `Content-Length` is dropped on one or both answers, the size comparison is skipped and says so in the report. The one case where it would pass while wrong is both answers carrying a `Content-Length` while the edge passes through a gzip body for the plain request with `Content-Encoding` missing; that is covered by the plain body failing to parse.
- Sending `Accept-Encoding: identity` with the plain request is sound: it asks any hop not to encode, and the server does not read it.
- A gap I accept: the gate cannot tell a server that compresses correctly from an edge that compresses by itself. It judges compression by `Content-Encoding` and relative size, and the edge has no compression on `/v1` anyway.
